# Participation access

Users have independent participationEnabled (default false), participationRevision and last-change time. Existing missing values are backfilled false without resetting explicit values. Account active/disabled status remains separate. Event participationRequired defaults false, persists across restarts and changes only by main-admin commands.

Main admin: Participation page lists users and controls the master rule. Staff accounts can provision a Participation Manager (participation_admin) with participation.read and participation.update. Other roles receive neither capability. Managers may enable/disable individuals while the master is OFF; only main admin can change the master. The list uses bounded email-prefix search, filters, 25-row cursor pages and safe field projection. PATCH uses explicit enabled boolean, per-user revision and actor/target/value-bound operation receipts. Old retries return current state and cannot undo newer changes. All changes are audited.

Master OFF bypasses only the new condition. Master ON requires participationEnabled exactly true for creating King/Queen ballots, Lantern votes and Memory Photo submissions. Authentication, final-vote rules, event windows, candidate validity and quotas still apply. Existing same-choice vote receipts may acknowledge a recorded vote without writing another. Flag changes do not reset rounds/windows or existing choices.

Wish Sky, photo likes/unlikes, photo history and existing owner archive/restore/delete controls are independent and retain existing feature/auth rules. Access changes never delete submitted content, change moderation state or reset quota slots. Two free slots remain two free slots while uploading is restricted. Re-enabling participation or turning master OFF restores eligibility, not extra votes or quota.

Protected writes and access changes share the existing database controls fence. The commit that wins defines whether an unfinished action is accepted. Photo processing/storage happens outside the transaction; final acceptance rechecks account/session, current participation access and feature enablement in a short transaction. Conclusive failures use existing durable cancellation/slot cleanup only for that new request. Uncertain commits retain existing reconciliation safeguards. An isolated fixture-only IPC barrier verifies revocation during storage, preservation of the first photo and release of only the failed slot.

PARTICIPATION_REQUIRED is an explicit safe error reason carried to the frontend. Students remain signed in, see an organiser-contact message, retain upload previews, and refresh permissions on focus/periodically without a new login. The backend is authoritative for every submission.

Release manifests include participationAccess:1. The root-installed release-policy.py must match this compatibility before deployment. Older code lacks both enforcement and recognition of the new staff role; automatic rollback to that code is refused. Keep a known-good participation-aware release for future rollback. Initial deployment leaves master OFF; no manager account or grant is created automatically. Enable enforcement only after verification and after ensuring no old backend can write the same live database.

Tests: master matrix, safe user list, role isolation, revisions/receipt retries, persistence, real King/Queen/Lantern/photo submissions, unchanged content/quota, independent wishes/likes/owner controls, revocation during storage, and a desktop/student plus mobile/admin browser flow. Existing auth, memory, announcement, release and proxy regressions remain required. No production test votes, photos or emails are used.
